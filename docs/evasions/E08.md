# E08: The payload at the end of a command line longer than the capture limit

Predicted (design, section 8): **partial**. Measured: **detected**. Measured results of every run are in [../evasion.md](../evasion.md).

## What was measured

- `python3 -c` with 1,500 bytes of comment before the code that opens `/etc/shadow`; the exec event keeps the first 1,024 bytes of argv.
- R005 fired: no shipped rule matches on the command line, so truncation did not cost the alert. The prediction (partial) is corrected to detected.
- What it cost is the evidence: the alert's `process.CommandLine` ends in the padding, and the payload is not in it.
- The alert is a file_open record, which does not carry `argv_truncated`; only the exec record does. Someone reading the alert is not told that the command line was cut.

## Why

The exec event keeps the first 1,024 bytes of argv. A program that puts its payload after a long run of padding (here, a comment in a `python3 -c` script) leaves only padding in the captured command line.

It did not cost the alert, because no shipped rule matches on the command line: the detections that matter here are on behaviour (the open of `/etc/shadow`), and that event does not depend on argv at all. The prediction of "partial" assumed command-line rules; the measured result is "detected", and the prediction is corrected.

What it did cost is the evidence. An analyst reading the alert sees `python3 -c "# AAAA…"` and not what the script did. Worse, nothing in the alert says the command line was cut: the truncation flag is on the exec record only, and the alert is a file_open record, which carries the process's command line from the process tree without the flag.

## Proposed fix

1. **Carry the flag with the command line.** Store `argv_truncated` in the process tree with the command line, and put it on every record that carries `process.CommandLine`, not only on exec records. Cheap, and it makes the gap visible wherever the command line appears.
2. **Keep the end as well as the start.** When argv is longer than the buffer, capture the first 768 and the last 256 bytes, with a marker between them. Payloads are usually at the end of a padded command line, because the padding has to come first. The exec program already knows the total length.
3. **A rule on suspiciously long command lines** of interpreters (`-c` or `-e` with more than the capture limit), at low level: padding is itself a sign of evasion.
