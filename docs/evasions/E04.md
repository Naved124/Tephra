# E04: Open /etc/shadow through io_uring instead of the open system call

Predicted (design, section 8): **detected**. Measured: **detected**. Measured results of every run are in [../evasion.md](../evasion.md).

## What was measured

- A single `IORING_OP_OPENAT` of `/etc/shadow`, submitted on a ring set up with raw system calls; the pod ran with the seccomp profile `Unconfined`.
- R005 fired on python3's open of `/etc/shadow`, `matched_by: inode`. The file_open hook is at `security_file_open`, which an open through io_uring passes like `openat(2)`.

## Why

io_uring lets a program queue operations, an open included, without making the system call for each one; the kernel carries them out from its own worker context. A sensor that hooks system calls (`sys_enter_openat` and friends) never sees these opens, which is why io_uring is a known blind spot of syscall-based tools.

Tephra's file_open program is attached to `security_file_open`, the LSM hook that every path to opening a file goes through, because it is where the kernel checks permissions. An io_uring open reaches it like any other. The event names the process that submitted the request and the file that was resolved, and R005 fires as for `cat`.

The pod ran without the runtime's default seccomp profile. Containerd's default profile may refuse the io_uring system calls; with it, the technique would have been stopped before the sensor mattered. The scenario turns that off so that what is measured is the sensor.

## Proposed fix

None needed for this case. The point to keep is a design rule already followed: hook the security layer, where the kernel has resolved the object, and never the system call layer. Any future hook (for example on connect or on file permission changes) should follow it, and E04 should be kept in the harness as the regression test for it.
