# E26: Move into another pod's cgroup and mount namespace, then read /etc/shadow

Held out. Predicted (design, section 8): **missed**. Measured on 5.15 (Phase 5, run 2): **missed**, for a reason the prediction did not foresee. Results: [../runs/2026-11-22-5.15/evasion.md](../runs/2026-11-22-5.15/evasion.md).

## What was measured

- A privileged pod with the host's process namespace and the node's cgroup tree found a bystander pod's process, wrote its own shell's pid into the bystander's `cgroup.procs`, then ran `nsenter -t <bystander> -m cat /etc/shadow`.
- **All three rules meant for this fired**, within a millisecond of each other: R034 (a pod moved a process into a cgroup), R036 (a process entered another pod's mount namespace) and R005 (`/etc/shadow` read).
- **None of them named the attacker's pod.** Every record of the attacker, including its shell *before* the move, carried `process.identity_mismatch: true` and was filed under namespace `unknown` with no pod. The harness looks for an alert naming the scenario's pod, found none, and reported a miss.

## Why

The container it was relabelled to, `d712001d7b84…`, was **E23's victim**, a pod of the scenario before, already deleted. Three things lined up:

1. **E23 dropped the exit events.** E23 floods the node while the agent is dead; 1,055,986 records were dropped from the full ring buffer, among them the exits of E23's own processes. The agent's process tree kept those processes as alive.
2. **Linux reuses namespace numbers.** A mount namespace is named by an inode number in the kernel's nsfs, and freed numbers are handed out again. E26's attacker pod got the mount namespace number E23's victim had.
3. **The borrowed-identity check (3.2) trusted the oldest live process in a mount namespace** as that namespace's owner. For a process born from the runtime, as a `kubectl exec` is, the owner of its mount namespace decides which container it "came from". The oldest "live" process in that namespace number was one of E23's ghosts, so every process of E26's attacker was judged to have come from a container that no longer existed, and was named under it.

So the fix for borrowed identity made a worse mistake possible: after lost exits and a reused number, a pod's activity is credited to a dead pod. The detection itself held; the attribution failed.

E26 also shows the order of scenarios matters: it ran directly after a flood. That is not a harness fault: an attacker can do the same, flooding first so that exits are lost, then working from a pod that inherits a dead pod's namespace number.

## Proposed fix

1. **Check that a namespace's owner is really alive** before trusting it: its `/proc/<pid>` entry exists, with the same start time and the same mount namespace. A ghost found this way is marked exited and the next candidate is tried.
2. **Clear ghosts after drops.** When the ring buffer reports drops, or an agent adopts a backlog, check the tree's live processes against `/proc` once, so that lost exits do not linger.
3. **Never relabel to a container the pod index does not know.** If the container a process supposedly came from is unknown to Kubernetes, keep the cgroup's attribution and mark the mismatch, rather than turning a known pod into `unknown`.
4. **Test:** a tree with a ghost in a namespace number, a new pod reusing it, and the attacker's records named under the new pod; and E26 run again directly after E23 as a check after the fix.

The held-out result stands as measured.
