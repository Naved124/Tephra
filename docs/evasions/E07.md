# E07: Kill the agent on the node, read /etc/shadow, let the agent restart

Predicted (design, section 8): **missed**. Measured: **missed**. Measured results of every run are in [../evasion.md](../evasion.md).

## What was measured

- A privileged pod with the host's process namespace found the agent's process on its node through `/proc`, killed it with SIGKILL, and read `/etc/shadow` straight away.
- R005 did not fire. The agent container restarted once during the scenario (the harness's restart count), and no alert for the read reached Loki.
- No other rule fired in the namespace: the kill itself (a signal from a privileged container to a process outside it) is not an event the sensor observes.
- First run: invalid. busybox's `pgrep -x tephrad` found nothing, the script stopped before acting, and the harness reported a miss for a technique that never ran. The scenario now finds the agent through `/proc`, and the harness treats exit status 99 from a scenario as "not carried out" instead of judging it.

## Why

The sensor's programs and its ring buffer live in the kernel, but everything after the ring buffer is in the agent process: decoding, attribution, rules and export. While the agent is down the BPF programs are detached (they are not pinned in detect mode) and nothing is recorded. A read that happens in that window is not buffered anywhere and is not reported when the agent returns. Kubernetes restarts the container within seconds, which is why the window is short, but an attacker who can kill the agent can act inside it reliably: kill, act, done.

Being able to kill the agent at all requires what this pod had: privilege and the host's process namespace, which is a container escape already. So E07 is about what remains visible after an escape. What is visible is the restart: the agent container's restart count goes up, and the agent logs a fresh start. Nothing names the action taken during the gap.

With enforcement on and the default pinned mode, the refusals are different: the LSM programs and their policy maps are pinned in the kernel and keep refusing while the agent is down. That closes the blocking half of this evasion for the six blockable actions; it does not make the detection of other actions survive.

## Proposed fix

1. **Make the gap an alert, not just a counter.** A restart of the agent container should itself raise a high-level alert from the collector (which sees a stream end and a new one begin from the same node) and from the dashboard's alert rules, naming the node and the length of the gap. Today it is only a restart count.
2. **Keep recording while the agent is down.** Pin the detection programs and the ring buffer the way enforcement is pinned, so that the kernel side keeps filling the buffer during a restart and the new agent drains it. The buffer then covers a gap as long as it takes to fill (16 MiB is tens of thousands of events), and the new agent attributes the old events from `/proc` seeding. This is the larger change; it moves the agent's restart from a blind spot to a delay.
3. **Watch the watcher.** A small rule on signals: a kill of the agent's process from any other cgroup, reported from a hook on `security_task_kill`. It fires before the agent dies; the kernel delivers the event to the ring buffer even if the agent never reads it, so it is useful only together with fix 2.
