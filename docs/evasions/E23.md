# E23: Flood alerts from 200 differently named programs, kill the agent, read /etc/shadow

Held out. Predicted (design, section 8): **partial**. Measured on 5.15 (Phase 5, run 2): **detected** by the held-out rule (R030 and R031 named the node), but **the read itself was lost**. Results: [../runs/2026-11-22-5.15/evasion.md](../runs/2026-11-22-5.15/evasion.md).

## What was measured

- A flooder pod copied `cat` to 200 names and read `/etc/shadow` with them in a loop, so that grouping by program could not merge the alerts. A second, privileged pod killed the agent and then read `/etc/shadow` itself.
- R030 fired on the kill, and R031 on the agent's unannounced restart. The held-out rule counts an alert about the node, so the scenario is "detected".
- **R005 never named the victim.** Every R005 that arrived names the flooder: tens of thousands of them, grouped into summaries, with the per-pod budget folding the flooder's 200 programs as designed.
- The ring buffer dropped **1,055,986 records**.

## Why

Phase 5's fix for drowning the alert (3.1) works on what reaches the agent: grouping, the per-pod budget, and a queue that drops the lowest level first. All three did their job on what arrived.

The victim's read never arrived. While the agent was dead, the pinned ring buffer kept recording, which is the Phase 3 fix that lets a new agent read what happened while none ran. But the flood kept recording too. A ring buffer is first come, first served: once full, every new record is dropped, whatever it is. The flood filled the 16 MiB buffer, and the victim's read, which came after the kill, found the buffer full.

E19, the same attack with one flooding program, was caught on the same run. The difference is timing: whether the victim's read lands before the buffer fills. An attacker can make sure it does not.

So the class "drown the alert" has a second place to drown it: the kernel's buffer while no agent reads it, before any of the agent's defences apply.

## Proposed fix

1. **A small reserved buffer for what matters.** A second ring buffer, a few hundred KiB, for records that watched files, the agent's own protection hooks or privilege changes produce, so a flood of one kind cannot push them out. Floods mostly come from the cheapest events to cause.
2. **Rate limits per cgroup in the kernel**, for the event types an attacker can generate cheaply (opens of watched files, connects): beyond a budget per second, a cgroup's records are counted rather than sent, and the count is reported. One pod's flood then cannot fill the buffer for others.
3. **Name the loss.** Drops are counted per event type today. Counting them per cgroup too would at least say whose records were lost.
4. **Test:** the E23 replay at kernel level: fill the buffer from one cgroup with no reader, then open a watched file from another, and check the second record survives.

The result stands as measured: detected by the held-out rule, and recorded here as a real limit of the drowning fix.
