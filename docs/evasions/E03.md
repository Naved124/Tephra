# E03: Read /etc/shadow through a hard link under an unwatched name

Predicted (design, section 8): **detected**. Measured: **detected**. Measured results of every run are in [../evasion.md](../evasion.md).

## What was measured

- First run: invalid. The link was made inside the judged window, and the alert counted was `/bin/ln` opening `/etc/shadow` itself (`matched_by: path`), not the read through the link. The scenario now makes the link when the pod starts.
- Rerun: `cat /tmp/notes.txt`, where `/tmp/notes.txt` is a hard link to `/etc/shadow`. R005 fired on the open by `/bin/cat`; the record has `file.path` `/tmp/notes.txt`, `file.target` `/etc/shadow` and `matched_by: inode`. The event came 64 ms after the start of the technique.

## Why

A hard link is a second name for the same file. A sensor that filters file opens by path compares the name that was opened with the names it watches, and `/tmp/notes.txt` is not one of them, so a path-only filter misses the read even though the bytes read are those of `/etc/shadow`.

Tephra watches a file two ways. Besides the path, the agent resolves every exact-path watch to its device and inode number in each container's root filesystem and writes those to an inode map in the kernel. The file_open program looks up the opened file's identity there as well as its name. A link shares the identity, so the open is reported and the agent names the watched file in `file.target`; rules that test `file.path` match either name.

The first run of this scenario showed a second, quieter point: making the link opened `/etc/shadow` too (busybox's `ln`, on overlayfs), and that alone already raised R005. Preparing the evasion is itself visible.

## Proposed fix

None needed for exact-path watches. Two limits remain and are worth stating:

1. **Prefix and name watches are by name only.** A file under a watched prefix (`/etc/cron.d/`) or with a watched name (`authorized_keys`) reached through a link from elsewhere is not recognised, because there is no fixed set of identities to resolve in advance. For write rules this matters less (writing through a link to a cron file still changes the cron file, and R023 catches a link created onto a watched name), but a read-only rule on a prefix has the gap.
2. **Links made before the agent started** are covered only because identities are resolved at start and on every new container root; that resolution should be retested after the agent restarts while a link exists (E07's window).
