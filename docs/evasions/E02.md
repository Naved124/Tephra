# E02: Interactive session implemented inside Python, no shell executed

Predicted (design, section 8): **missed**. Measured: **missed**. Measured results of every run are in [../evasion.md](../evasion.md).

## What was measured

- A Python process read commands from a TCP socket and carried them out with Python calls (directory listing, file read). Nothing was executed.
- R001 did not fire, and no other rule fired in the namespace.
- The connection went to 127.0.0.1 and the files read are not watched; neither is reported by design (net_ignore and the file watches).

## Why

Every exec-based detection assumes that doing something means starting a program to do it. An interpreter breaks that assumption: Python, Node, Perl and Ruby can list directories, read files, open sockets and change permissions without ever calling `execve`. The session in this scenario is, from the kernel's point of view, one long-running `python3` with an open TCP connection that reads a few files.

None of those actions crosses a line the sensor watches. The connection went to an address that is not the Kubernetes API, a runtime socket or a mining port; the files read are not watched. This is by design: watching every connect and every open would cost far more than the sensor's budget, and the false-positive run shows that ordinary workloads do both all the time.

So this is a limit of the approach, not a bug. What an exec sensor can see of an in-process session is its effects on the few resources that are watched, and the shape of the process: an interpreter that holds a network connection and was not the container's main process.

## Proposed fix

1. **Interpreter with a network peer, not the main binary.** Report, at low or medium level, an interpreter (by image name, and by content identity once E01's fix exists) that is not the container's main binary and makes an outbound connection. Most of a typical cluster's interpreters are main binaries (a Python web app), so the main-binary exclusion keeps the volume down. It needs a connect event for every outbound connection from processes that match, which means a kernel-side filter on "this process is an interpreter that is not the main binary": a map of interpreter inodes, filled by the agent, checked in the connect program.
2. **Rely on the watched effects.** The things an attacker comes for are mostly already watched: credentials (R005, R006), persistence paths (R007 to R009), the runtime socket (R010), the API (R013). E02 shows that the session itself is invisible, not that its consequences are; the write-up of the detection model should say so plainly.

The first makes the session itself visible at a measured cost; it should not be shipped without a false-positive run on a workload with an interpreter that is not its main process (a Jupyter pod is the hard case).
