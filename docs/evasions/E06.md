# E06: Rewrite the path argument from a second thread while openat runs

Predicted (design, section 8): **detected**. Measured: **detected**. Measured results of every run are in [../evasion.md](../evasion.md).

## What was measured

- One thread opened the name in a shared buffer in a loop for two seconds; another flipped the buffer between `/etc/shadow` and `/etc/hostx` (which does not exist).
- R005 fired on an open of `/etc/shadow` (`matched_by: inode`). The path and identity in the event are the ones the kernel resolved, read at `security_file_open`, not the user buffer.

## Why

The race in this scenario targets sensors that read the system call's arguments from the process's memory at entry: the sensor reads the path, the attacker's second thread changes the bytes, and the kernel then reads the changed bytes and opens a different file. The sensor reports one file while another was opened, a classic time-of-check to time-of-use gap.

Tephra never reads a path from user memory for a file event. The file_open program runs at `security_file_open`, after the kernel has copied the name, walked the path and opened the file; it reads the path from the kernel's own `struct file` and the identity from the inode. Whatever the second thread does to the buffer, the event describes the file that was actually opened.

## Proposed fix

None needed. As with E04, this is a design rule to keep: read objects the kernel has resolved, never user pointers. The same applies to the enforcement programs, which make their decisions at LSM hooks for the same reason (section 9 of the design). E06 stays in the harness as the regression test.
