# E05: Flood the sensor with short-lived processes, then read /etc/shadow

Predicted (design, section 8): **detected**. Measured: **detected**. Measured results of every run are in [../evasion.md](../evasion.md).

## What was measured

- Eight parallel loops of 4,000 `/bin/true` each (32,000 execs) on a 4-vCPU node; `/etc/shadow` read two seconds in.
- R005 fired. The ring buffer reported zero drops over the scenario: 16 MiB of ring buffer and this rate of execs did not fill it on this machine.
- Not tried: a flood of the event type the attack itself needs, or a larger flood.

## Why

The idea of the flood is to fill the ring buffer between the kernel and the agent with harmless events, so that the event of the real action is dropped. Two things defeated it here.

First, the buffer was large enough: 16 MiB at about 400 bytes per exec event holds some 40,000 events, and the agent drains it continuously, so 32,000 execs over a few seconds on four vCPUs never filled it. Second, the action used another event type: the file open of `/etc/shadow` is filtered in the kernel by watch, so only the opens of watched files compete for space, and an exec flood only delays them.

Had the flood won, the result would still not be silent: every dropped event is counted per type in the kernel and exported as `tephra_kernel_events_total{outcome="dropped"}`, and the dashboard shows it. That is the property the scenario checks for: either detection or a visible gap.

## Proposed fix

1. **Make the flood harder to win.** Size the ring buffer by node size (the default could scale with the number of CPUs), and give alert-relevant event types priority: a second, smaller ring buffer for the types that rules on watched objects use (file_open of watched files, ptrace, module_load, cred_change, enforce), so that an exec flood cannot crowd them out.
2. **Measure the edge.** Repeat the scenario with a flood ten and a hundred times larger, and with a flood of the same type as the action (opens of a watched file), to find where drops start. That number belongs in the benchmark report.
3. **Alert on drops.** A rule-level alert, not only a metric, when drops occur on a node: a flood is itself a sign of an attack.
